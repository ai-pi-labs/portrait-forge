# 一致性与版本

一致性分三层：档案不变、Prompt 不漏项、实际图片仍是目标外观。本项目自动检查前两层的编码部分，第三层需要看图。

建立一张用户认可的单人基线，保存 JSON 和实际参考资产编号。person、structure、skin 属于身份字段；固定脸任务将所有已登记身份值（包括 null 未知）写入 card.locks，不要补齐原稿未知项。服装、发型、妆、摄影是否锁定取决于具体任务，不默认都属于身份。

局部修改使用精确白名单：`makeup.lip_color` 与 `makeup.lip_finish` 是两项，不接受通配符。revise 复制基线，只替换 patch 指定字段；保留其他字段的值、状态、证据和缺失状态。新版本携带基线 SHA-256、允许项和完整差异。compile/validate 编辑版时提供相应基线，检查哈希和实际变化。哈希用来发现错版本，不是签名或用户授权证明。

跨会话：用户重新提供基线 JSON、当前版本和需要的实际图片。不要称角色编号为跨模型身份记忆，也不要声称自动持久保存。图片附件会话标识可能失效，应重新加载资产。

多角色：先定共用妆，再分别建脸。distinct=true 比较所有配对，输出每对差异组；亲缘或相似目标用 distinct=false，不强求差异，但需要人工审查相似关系。至少一个核心差异组被全部锁死时先计算剩余空间。默认三组差异中至少两核心组；锁定不允许实现时报告具体缺口，不能用发色或痣凑分。

多轮修改保留每一步 JSON；第 N 版只需提供第 N-1 版作本次基线验证。整条历史审计则逐步验证每一对。程序不能替用户判断 allow 列表是否真的来自本轮意图，Agent 必须核对原请求。

生成后按优先顺序看：人物数量、已锁定脸部/肤色/标记、妆容落点、本轮修改、摄影边界。逐项标“符合/偏离/看不清”。只在结果实际可见时评价；保留偏差证据，用户要求继续时一次修正明确问题。
